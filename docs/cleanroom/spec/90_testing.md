# 90 受け入れテスト計画

## この章の範囲
この章では、クリーン実装が仕様どおりに動くかを確かめる方法を定める。各章の末尾にある「受け入れテスト観点」を横断してまとめ、マイルストーンとテストハーネスの使い方を示す。

前提となる章: 全章。ヘッドレス実行器の仕様は 01_platform_common.md にある。

## 1. テストハーネス

クリーン実装には、画面を持たない **ヘッドレス実行器** を必ず用意する（仕様は 01 章）。最低限、次の機能が要る。

- 引数に、ゲームのディレクトリと入力スクリプトを取る。
- スクリプトに書かれたキー入力を、指定したフレーム（VSYNC）に注入する。
- スクリプト中の `shot:名前` の位置で、640×400 の画面を PNG で保存する。
- 音声出力を WAV で保存する。
- 乱数のシードを指定できる（D2 は既定値 1。D1 は起動時に常に 1 で初期化する）。
- デバッグ用の開始オプション: 指定のマップと座標へワープ、指定の敵グループと即戦闘、所持金の設定、アイテムの追加。
- 最大フレーム数に達したら終了する。

入力スクリプトの書式（既存実装と同じにしておくと、参考画面と比べやすい）:

- 数字 N: N フレーム待つ。
- `z`: 決定キーを 1 フレーム押す。`x`: 取消。`u` `d` `l` `r`: 上下左右。`q`: D1 のメッセージ早送り。`c`: Ctrl。
- `キー*N`: N フレームのあいだ押し続ける（例: `r*40`）。
- `shot:名前`: 画面を保存する。`quit`: 終了する。

## 2. マイルストーン

| 段階 | 完了条件 |
|---|---|
| M0 基盤 | パレットとプレーン形式の画像を正しく表示できる。テキスト層、フォント、Shift-JIS の描画が動く。ヘッドレス実行器で PNG を保存できる |
| M1 音源 | 全サンプルゲームの BGM/*.MML がエラーなくコンパイルでき、演奏できる。SOUND.DAT のすべての効果音が鳴る。テンポ（タイマ周期）が仕様の計算式どおり |
| M2 D1 データ | D1 の全サンプル（20 本）で全データファイルを読み込める。タイトル画像、マップ、キャラクター、敵画像を画像として書き出し、目で見て崩れていない |
| M3 D1 フィールド | タイトル、ニューゲーム、画面切り替え、NPC の移動、イベント（文章、店、はい/いいえ、スイッチ）、メインメニュー、セーブ/ロードが動く |
| M4 D1 戦闘 | エンカウント、コマンド入力、ダメージ計算、魔法、敵の AI、勝利と全滅が動く |
| M5 D2 データ | D2 の全サンプル（23 本）で全データファイルを読み込める。RPG.EXE の版の判別結果が 20 章の表と一致する |
| M6 D2 フィールド | スクロールするマップ、層、NPC、乗り物、エンカウント、色調の変化が動く |
| M7 D2 イベント | 22 章の全コマンドが動く |
| M8 D2 メニュー | 23 章の全メニュー、店、宿、セーブ/ロード、デバッグメニューが動く |
| M9 D2 戦闘 | 24 章の戦闘がすべて動く（敵の AI、オートバトル、変身、カウンターを含む） |
| M10 通し | 各サンプルゲームを、少なくとも最初の数イベントと最初の戦闘まで通して遊べる |

## 3. 参考スクリーンショット（reference_shots/）

`reference_shots/<ゲーム名>/` には、既存実装（参照実装）のヘッドレス実行器で各サンプルゲームを動かして撮った画面が入っている。全ゲームに同じ入力スクリプトを使った。

```
60 shot:01_title 30 z 30 z 150 shot:02_start z 70 z 70 shot:03_after_ok x 60 shot:04_menu x 60 r*40 l*40 shot:05_walk
```

条件は、D2 の乱数シードが 1（既定値）、最大 1500 フレーム、タイトル画像あり。

| ファイル | 撮った時点 |
|---|---|
| 01_title.png | 起動から 60 フレーム後。タイトル画像、またはオープニング |
| 02_start.png | 決定キーを 2 回押してから 150 フレーム後。多くのゲームではニューゲームの直後 |
| 03_after_ok.png | さらに決定キーを 2 回押した後。最初のメッセージが進んだところ |
| 04_menu.png | 取消キーを押した後。メニュー、またはメッセージの途中 |
| 05_walk.png | 右へ 40 フレーム、左へ 40 フレーム移動した後 |

使い方と注意:

- これらは **既存実装の出力** であり、原本（PC-98 の実機）との一致は保証されていない。互換性の正解ではなく、大きな食い違い（レイアウトが崩れる、色がずれる、進行が止まる）を見つけるための参考に使う。
- 文字のグリフは東雲フォントのもの。
- タイトルとオープニングの長さはゲームごとに違うので、同じスクリプトでも画面の状況はゲームによって異なる。
- 比べるときは、まず画素単位で差分を取り、差のある領域を目で確かめる。差の原因が「仕様の解釈の違い」なのか「仕様の不備」なのかを記録し、後者は汚染側に問い合わせる。

### 3.1 参考音声（reference_audio/）

既存実装で、次の条件で録音した WAV を置いている（44100 Hz、16 ビット、ステレオ、900 フレーム分）。

| ファイル | ゲーム | エンジン | MUSIC.COM の版 |
|---|---|---|---|
| come.wav | come | D1 | 2.00 |
| agasa.wav | agasa | D1 | 2.00 |
| kokoro.wav | kokoro | D2 | 2.21 |

入力スクリプトは `100 z 100 z 100 z 100 z 400`。参考画面と同じく、互換性の正解ではなく、大きな食い違いを見つけるための参考として使う。

## 4. 横断テスト項目

### 4.1 データ読み込み（全サンプルゲーム）
- 全ゲームについて、データファイル（10 章、20 章に載っているもの）をすべて読み込み、レコード数と主要フィールドの値域が仕様の範囲に収まることを確かめる。
- ファイル名の大文字小文字が混在していても見つかる。
- 存在しない任意ファイル（タイトル画像、ピクチャ、BGM など）があっても異常終了せず、仕様どおりにフォールバックする。

### 4.2 画像
- D1 / D2 のすべての画像形式を PNG に書き出し、崩れがないことを目で確かめる（プレーンの順序、マスク、パレット）。
- パレットの 4 ビット値から 8 ビット値への変換が仕様どおり（01 章）。

### 4.3 音
- 全ゲームの全 MML をコンパイルし、エラーの件数を記録する。既存実装でエラーになるものがあれば、仕様書の「未確認事項」と照らし合わせる。
- テンポ T と、タイマの周期、1 拍の長さの関係を数値で確かめる。
- 効果音の優先度による割り込み、効果音が終わった後に SSG チャンネルが元に戻ること、MUSIC.COM の版（2.00 / 2.21）による違い。

### 4.4 計算式（ユニットテスト）
- 経験値テーブル、レベルごとのステータス、ダメージ式、ばらつき関数、逃走判定、敵の AI の評価値は、仕様の式をそのままテストケースにする（入力値と期待値の表を作る）。
- 乱数: シード 1 から引いた最初の数十個の値を固定値と比べる（線形合同法の定数の検証）。

### 4.5 セーブ互換
- セーブ形式は原本と同じバイトレイアウトにする（10 章、20 章）。実装でセーブし、ロードし、もう一度セーブしたとき、ファイルがバイト単位で一致すること。
- 原本で作ったセーブデータがある場合は、それを読み込めること。

### 4.6 版の違い（D2）
- 20 章の版判別表のとおりに、各サンプルの RPG.EXE が判別されること。
- 版ごとの差（20 章に一覧がある）のそれぞれについて、該当する版のゲームで挙動が切り替わること。

### 4.7 タイミング
- 移動 1 歩あたりのフレーム数、メッセージの表示速度、待ちコマンドのフレーム数、SHIFT キーによる加速、早送り（Tab キー）。

## 5. 不具合を報告するときの書式

クリーン側が仕様の不備を見つけたら、次の項目を書いて汚染側に送る。

- 該当する章と節
- 再現手順（ゲーム名、入力スクリプト、シード）
- 期待した挙動と、仕様書の記述
- 観察した挙動（あれば、参考スクリーンショットとの差）
- 仕様が曖昧だと考える点
